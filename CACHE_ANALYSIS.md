# Анализ кеширования Next.js и Vercel

## 1. Текущее состояние

### next.config.ts
- **headers()** — не заданы. Управления Cache-Control из конфига нет.
- **redirects()** — есть (www → основной домен, http → https). Не трогаем.

### vercel.json
- Заданы только security-заголовки для `(.*)`:
  - `Strict-Transport-Security`
  - `X-Content-Type-Options: nosniff`
  - `X-Frame-Options: DENY`
- **Cache-Control** в vercel.json не задаётся.

### Поведение Next.js по умолчанию (документация)
- Для **иммутабельных статиков** (`/_next/static/` с хешем в имени файла) Next.js сам выставляет:
  - `Cache-Control: public, max-age=31536000, immutable`
  - **Эту настройку из next.config переопределить нельзя** — заголовок выставляется фреймворком.
- Для HTML-страниц и прочих ответов своих дефолтов по Cache-Control в конфиге нет, их можно задать через `headers()`.

---

## 2. Цели

| Цель | Решение |
|------|--------|
| Файлы `/_next/static` кешируются долго | Next.js уже даёт `immutable` для хешированных файлов. При добавлении глобального Cache-Control нужно **не перебивать** статику: задать правило для `/_next/static/:path*` с `public, max-age=31536000, immutable` и располагать его **после** общего правила. |
| Остальные пути — revalidate | Добавить в `headers()` правило с `source: '/(.*)'` и `Cache-Control: public, max-age=0, must-revalidate`. |

---

## 3. Важно: порядок правил в headers()

В Next.js при нескольких совпадениях по одному пути **побеждает последнее** правило с тем же заголовком:

- Если сначала идёт `(.*)` с `max-age=0, must-revalidate`, а потом `/_next/static/:path*` с `immutable`, то:
  - для `/_next/static/...` применится **второе** правило → статика остаётся с долгим кешем;
  - для `/`, `/analizy` и т.д. совпадёт только первое → будет `must-revalidate`.
- Если сделать наоборот (сначала статика, потом `(.*)`), то для статики применится общее правило и долгий кеш будет перезаписан.

Итог: в конфиге сначала — общее правило для `(.*)`, затем — явное правило для `/_next/static/:path*`.

---

## 4. Vercel

- vercel.json **не меняем**: не добавляем туда Cache-Control, чтобы не дублировать и не конфликтовать с next.config.
- Кеширование статики и страниц будет управляться только через `headers()` в next.config.ts.

---

## 5. Что не трогаем

- layout, API, routing, SEO — без изменений.
- redirects() в next.config — без изменений.
- vercel.json — только security-заголовки, как сейчас.
